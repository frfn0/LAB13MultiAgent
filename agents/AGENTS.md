# Агенты системы техподдержки

Методичка требует выделить не менее трёх типов агентов и для каждого
определить роль, входные данные, выходные данные и бизнес-правила.
В варианте 2 предметной областью является автоматизация техподдержки, а
набор ролей задан преподавателем: классификация тикетов, поиск по базе
знаний, генерация ответов, эскалация.

Реализованы все четыре роли. Первые три образуют конвейер: тикет
разбирается, ищется решение, формируется ответ. Четвёртая включается,
если конвейер не справился.

---

## Агент 1. Классификация тикетов

| | |
|---|---|
| **Роль** | Определить, к какой категории относится обращение клиента |
| **Вход** | Текст обращения `ticket.text` |
| **Выход** | `category`, `priority` (1–5), `tags`, `needs_escalation` |
| **Реализация** | `agents/classifier/main.go` |

### Бизнес-правила

1. Категории: `billing` (оплата), `technical` (ошибки), `account`
   (доступ, пароль), `delivery` (доставка), `other`.
2. Приоритет выставляется по совпадению ключевых слов:
   - `blocked`, `не работает`, `упал`, `500` → приоритет 5;
   - `оплата`, `счёт`, `возврат` → приоритет 4;
   - `пароль`, `доступ`, `аккаунт` → приоритет 3;
   - остальное → приоритет 1.
3. Запрос помечается для эскалации, если не найдена база знаний либо
   категория `other`.
4. Обрабатываются и `blocked`, `password`, `пароль` — регистр не учитывается.

---

## Агент 2. Поиск по базе знаний

| | |
|---|---|
| **Роль** | Найти в базе знаний решение, подходящее к обращению |
| **Вход** | `ticket.text`, `category` от агента классификации |
| **Выход** | `article_id`, `title`, `solution`, `confidence` |
| **Реализация** | `agents/knowledge/main.go` |

### Бизнес-правила

1. Оценка релевантности — доля слов запроса, встречающихся в статье.
2. Статья подходит, если `confidence >= 0.25` (порог задаётся переменной
   окружения `MIN_CONFIDENCE`).
3. При нескольких подходящих выбирается наибольший `confidence`;
   при равенстве — наименьший `article_id`, чтобы выбор был
   воспроизводимым.
4. Если ничего не найдено, возвращается `found: false` — это сигнал
   для эскалации, а не ошибка.

---

## Агент 3. Генерация ответов

| | |
|---|---|
| **Роль** | Сформировать текст ответа клиенту |
| **Вход** | `category`, найденная статья `article` |
| **Выход** | `answer` (текст), `answer_type` (`resolved` или `deferred`) |
| **Реализация** | `agents/responder/main.go` |

### Бизнес-правила

1. Если статья найдена — ответ шаблонный, на основе её текста.
2. Если статья не найдена — формируется ответ о передаче вопроса
   специалисту, `answer_type: deferred`.
3. Ответ для категории `billing` всегда содержит упоминание сроков
   возврата, для `account` — инструкцию по восстановлению доступа.
4. Агент детерминирован: одинаковый вход даёт одинаковый ответ.
   Режим LLM не используется, LLM-подключение описано в задании 8.

---

## Агент 4. Эскалация

| | |
|---|---|
| **Роль** | Зафиксировать обращение, которое нельзя закрыть автоматически |
| **Вход** | `ticket`, `category`, `priority`, `reason` (почему эскалировано) |
| **Выход** | `escalation_id`, `assigned_to`, `sla_hours`, `status` |
| **Реализация** | `agents/escalation/main.go` |

### Бизнес-правила

1. `assigned_to` выбирается по категории:
   - `billing` → `отдел-расчётов`;
   - `technical` → `инженерная-служба`;
   - `account` → `служба-поддержки-аккаунтов`;
   - иначе → `старший-специалист`.
2. `sla_hours` зависит от приоритета:
   - приоритет 5 → 1 час, 4 → 4 часа, 3 → 8 часов, иначе 24 часа.
3. Приоритет 5 дополнительно помечается `urgent: true`.

## Как агенты общаются

Задачи и результаты ходят по NATS:

| Тема | Назначение |
|------|------------|
| `ticket.classify` | задание классификатору |
| `ticket.knowledge` | задание поиску по базе знаний |
| `ticket.answer` | задание генератору ответа |
| `ticket.escalate` | задание эскалирующему агенту |
| `ticket.result` | ответ с результатом задания |

Все задания для агентов одного типа публикуются в общую очередь группы
(queue group), поэтому несколько экземпляров одного агента делят нагрузку
между собой — это задание 7.

Оркестратор (`orchestrator/main.py`) управляет конвейером: отправляет
задание, ждёт ответ, при сбое повторяет попытку.

Порядок работы тикета:

```
тикет -> ticket.classify -> ticket.knowledge -> ticket.answer -> результат
                                    |
                                    +-> статья не найдена
                                              |
                                              v
                                       ticket.escalate
```

---

## Что не входит в вариант 2

Задание методички «Интеграция LLM-агента» относится к повышенной
сложности и в варианте 2 не выполняется. Агент генерации ответов
детерминированный: при одинаковом входе он выдаёт одинаковый ответ, что
удобно для тестирования.
