Раздача ответов сделана через одну подписку на общую тему `ticket.result` и
словарь ожидающих заданий, а не через отдельную подписку на каждое задание.
Причина: агенты публикуют результаты в общую тему, и оркестратор обязан
разнести их по идентификаторам.

Контракт сообщений на стороне Python (`orchestrator/messages.py`) повторяет

- Ответ, для которого нет ожидающего задания, не поднимает исключение, а
  пишет предупреждение в лог: иначе зависшее задание или повторный ответ
  приводили бы к падению обработчика подписки.
- При таймауте будущее удаляется из словаря ожидающих. Иначе поздний
  ответ агента остался бы в памяти и ушёл бы в пустоту.
- Счётчик `pending_count` и метод `wait_for_idle` добавлены сразу: они
  нужны для проверок в задании 9, где тесты оркестратора работают с
  моками NATS.
- Параметры повторов (`MAX_ATTEMPTS`, `RETRY_DELAY`) уже есть в настройках,
  хотя сами повторы появятся только в задании 6.

### Решения, принятые при проектировании

- Метрики публикуются по таймеру, а не в ответ на задание. Иначе в простое

  только `instance`, метрики агентов затирали бы друг друга. Эта же схема

- Счётчики в снимке не уменьшаются: перезапуск агента с нуля не должен
  обнулять накопленную статистику в оркестраторе.
- Логи пишутся в консоль и в файл одновременно, а не в один из них: без
  консоли не видно ошибок при разборе, без файла теряется история.
- Библиотека `nats-python` переведена на `WARNING`, иначе её внутренние
  сообщения засоряют вывод демонстрации.

## Задание 6. Обработка ошибок и таймаутов

### Промпт

> начинай 6-е
>
> ну

### Результат

В оркестраторе реализована повторная отправка задания при сбое агента:
новый модуль `orchestrator/retry.py` с `RetryPolicy` и функцией
`send_with_retry`. Через неё проходят все четыре шага конвейера. При
повторе отправляется то же задание с тем же `task_id`, поэтому агент узнаёт
повтор по идентификатору. При исчерпании попыток наружу поднимается
последняя ошибка.

Таймаут ожидания результата задаётся переменной `TASK_TIMEOUT` и реализован
через `asyncio.wait_for` в `NatsConnection.send_task`.

Чтобы повторы было на чём показать, в агента добавлено управление сбоями:
`FAULT_FAIL_ATTEMPTS`, `FAULT_DELAY_MS` и `FAULT_DROP`. По умолчанию сбои
выключены, при включении агент пишет в лог предупреждение.

Счётчики мониторинга пересчитаны на попытки отправки, добавлен счётчик
повторов, таймауты учитываются по факту, включая те, после которых был
повтор.

### Решения, принятые при проектировании

- Повторов не больше трёх — это прочитано как «три попытки всего», а не
  «три повтора»: три повтора дали бы четыре отправки и превысили бы
  требование методички. Значение вынесено в настройку `MAX_ATTEMPTS`.
- Пауза между попытками растёт геометрически и разбрасывается на
  небольшую долю. Без разброса несколько обращений, упавших на одном
  агента, начали бы повторяться синхронно и добили бы его тем же потоком.
- Повтор делается и при таймауте, и при ошибке в ответе агента: «сбой
  агента» — это и молчание, и явная ошибка. Повтор при ошибке можно
  отключить настройкой `RETRY_ON_AGENT_ERROR`.
- При повторе сохраняется `task_id`. Новый идентификатор означал бы, что
  в логах одного обращения появилось бы несколько разных заданий и
  связать их было бы нечем.
- Искусственные сбои сделаны частью агента, а не отдельной программой:
  иначе пришлось бы держать вторую реализацию агента, которая отвечает иначе,
  чем настоящая.
- Счётчик отправок переведён на попытки, а не задания: иначе по мониторингу
  нельзя было бы отличить «три задания» от «одно задание с двумя повторами».

### Неудачные попытки и исправления

| Что пошло не так | Почему | Как исправлено |
|------------------|--------|----------------|
| Повторы не срабатывали: счётчик показывал 0 повторов, сбой агента не проявлялся | Кроме нужного экземпляра работал ещё один, здоровый, экземпляр того же агента. Оба стояли в одной группе очереди `responders`, и задания доставались здоровому | В демонстрации постоянные агенты больше не включают ответчик: он запускается заново на каждой фазе |

## Задание 8. Создание API для запуска задач

### Промпт

### Результат

Сделан REST API на FastAPI, который принимает обращение клиента, проводит его
через оркестратор и агентов и возвращает ответ: HTTP -> API -> оркестратор ->
агенты -> ответ.

Маршруты: `GET /health`, `GET /api/agents`, `POST /api/tickets`,
`POST /api/tickets/async`, `GET /api/tickets`, `GET /api/tickets/{id}`.
Документация OpenAPI формируется по схемам Pydantic и доступна на `/docs`.

Логика вынесена из HTTP-слоя в `api/state.py`: класс `AppState` отвечает за
подключение к NATS, метрики агентов и хранение результатов и не зависит от
FastAPI, поэтому его можно проверять в тестах без запуска сервера. Приложение
собирается функцией `create_app(state)`, которой в тестах передаётся состояние
с подменёнными зависимостями.

Коды ответа выбраны по смыслу сбоя: 200, 202, 422, 502, 503, 504.

Проверка выполняется демонстрацией `python -m api.demo_api`: она сама собирает
и поднимает агентов, запускает настоящий сервер отдельным процессом и ходит к
нему по HTTP, то есть проверяется весь путь целиком.

### Решения, принятые при проектировании

- Логика не живёт в обработчиках маршрутов. Иначе её нельзя было бы проверить
  без HTTP, а в задании 9 всё равно потребовались бы тесты.
- Состояние приложения передаётся в `create_app`, а не создаётся внутри: так
  тесты подставляют своё состояние и не требуют брокера.
- Ответы прогоняются через схему `TicketResponse`. Иначе в теле ответа не
  хватало полей, объявленных в документации: `assigned_to` приходил как `null`
  вместо пустой строки там, где эскалации не было.
- Таймаут агента отдаётся клиенту кодом 504, а ошибка агента - кодом 502.
  Оба случая нельзя отдавать одним кодом: по 502 виноват агент, по 504 -
  оркестратор не дождался ответа.
- Хранилище результатов ограничено 200 обращениями в памяти. Оно нужно только
  чтобы забрать ответ асинхронно принятого обращения; тянуть в проект
  хранилище ради этого не требовалось.
- Лишние поля в запросе запрещены (`extra="forbid"`): опечатка в имени поля
  больше не проходит молча.
- Middleware возвращает время обработки и в лог, и в заголовке
  `X-Process-Time-Ms`: клиенту полезно знать длительность ответа, не открывая
  тело.
