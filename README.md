Первый агент - классификатор тикетов. Он подписывается на очередь NATS,

### Как устроен агент

Общая обвязка вынесена в отдельный пакет, агент пишет только свою логику:

| Файл | Назначение |
|------|------------|
| `pkg/messages/messages.go` | типы сообщений `Task`, `Result`, темы NATS, константы категорий |
| `pkg/agent/agent.go` | подключение, подписка на очередь, разбор JSON, вызов обработчика, публикация результата, счётчики, graceful shutdown |
| `pkg/agent/writer.go` | запись лога одновременно в файл и в консоль |
| `agents/classifier/main.go` | правила классификации и функция `handleTask` |
| `agents/classifier/errors.go` | ошибка для пустого текста обращения |

Контракт: агент реализует `handleTask(messages.Task) (messages.Result, error)`.
Всё остальное делает базовый пакет.

### Порядок правил важен

Правила проверяются по порядку, и первое совпадение задаёт категорию.
Порядок выбран так, чтобы неоднозначные обращения попадали в более
серьёзную категорию: фраза «Не работает оплата картой» содержит и
«не работает», и «оплата», но проверяется первым правилом `technical` и
получает приоритет 5, а не 4. При алфавитном порядке правил приоритет был
бы занижен.

### Как устроен оркестратор

| Файл | Назначение |
|------|------------|
| `orchestrator/config.py` | настройки из переменных окружения: `NATS_URL`, `TASK_TIMEOUT`, `MAX_ATTEMPTS`, `RETRY_DELAY` |
| `orchestrator/messages.py` | модели Pydantic, повторяющие контракт из `pkg/messages/messages.go` |
| `orchestrator/client.py` | подключение к NATS, подписка на результаты, отправка заданий, ожидание ответа, таймауты |
| `orchestrator/main.py` | демонстрация: пять обращений и проверка таймаута |

### Раздача ответов по идентификатору задания

Агенты публикуют результаты в общую тему `ticket.result`, а не отвечают
адресно. Оркестратор подписывается на неё один раз и раздаёт ответы
ожидающим заданиям:

```python
self._pending[task.task_id] = future   # при отправке
future = self._pending.pop(task_id)    # при получении ответа
```

Ответ, для которого нет ожидающего задания, попадает в лог с
предупреждением и никого не будит — так система переживает зависшие задания
и повторные ответы.

### Обработка таймаутов

```python
try:
    result = await asyncio.wait_for(future, timeout=timeout)
except asyncio.TimeoutError as exc:
    self._pending.pop(task.task_id, None)
    raise TaskTimeoutError(...) from exc
```

При таймауте будущее удаляется из словаря ожидающих, чтобы поздний ответ
агента не остался висеть.

Таймаут проверен отправкой задания в тему `ticket.no_such_agent`, на
которую никто не подписан: оркестратор ждал ровно секунду и поднял
`TaskTimeoutError`.

### База знаний

`knowledge_base/articles.json` — десять статей по пяти категориям: две про
оплату, две про технику, две про доступ, две про доставку и одна для прочих
обращений. Агент загружает файл при старте.

### Правила поиска

1. Оценка релевантности — доля значимых слов запроса, встречающихся в
   статье.
2. Статья подходит при оценке не ниже `0.25` (`MIN_CONFIDENCE`).
3. При нескольких подходящих выбирается лучшая; при равенстве — меньший
   номер статьи, чтобы выбор был воспроизводимым.
4. Если ничего не найдено — `found: false`. Это сигнал для эскалации, а не
   ошибка.

Дополнительное правило: совпадение категории обращения со статьёй добавляет
`0.2` к оценке. Без этого запрос про оплату мог получить статью про
доставку, если в ней встретилось бы слово «заказ».

### Сопоставление слов по основе

Слова сравниваются не точно, а по основе: запрос «оплатить» находит статью
со словом «оплата». Точное сравнение дало бы нулевую выдачу на реальных
обращениях, где почти всегда есть окончание.

### Ошибка, найденная при первой проверке

Первая версия агента поиска **не нашла ни одной статьи**: уверенность всегда
была `0.2`, то есть ноль совпадений. Две причины:

1. `isWordRune` возвращала `true` для пробела и дефиса, а условие
   `beforeOK` требовало `!isWordRune`. Получалось, что совпадение на границе
   слова никогда не засчитывалось: перед словом всегда стоит пробел.
2. Сравнение было точным, поэтому «оплатить» не совпадало с «оплата».

Исправлено: слова разбиваются на список и сравниваются по основе — общая
часть не короче четырёх символов. После исправления уверенность стала
`0.8–1.0` для типовых обращений.

Ещё одно исправление по ходу проверки: при эскалации оркестратор показывал
клиенту автоматический ответ с пометкой `resolved`, хотя обращение ушло
человеку. Теперь при эскалации ответ подменяется уведомлением о передаче
в отдел.

## Задание 5. Логирование и мониторинг

### Что сделано

Агенты пишут структурные логи через `log/slog`: запись содержит время,
уровень, сообщение и атрибуты (`task_id`, `ticket`, `elapsed_ms`, `agent`,
`subject`, `queue`). Вывод идёт в stderr и, если задан `LOG_FILE`, в файл.

Агенты публикуют свои счётчики в тему `agent.metrics` раз в
`METRICS_INTERVAL` — в том числе когда заданий нет, поэтому по метрикам
видно, что агент жив. Оркестратор собирает снимки в
`orchestrator/metrics.py` (`MetricsCollector`) и ведёт свои счётчики:
отправлено заданий, заданий с ошибкой, таймаутов.

### Переменные окружения агента

| Переменная | Назначение | По умолчанию |
|------------|------------|--------------|
| `LOG_FILE` | путь к файлу лога | не задан, только stderr |
| `LOG_LEVEL` | `DEBUG` включает подробные записи | `INFO` |
| `METRICS_INTERVAL` | период публикации метрик | `5s` |
| `INSTANCE_ID` | идентификатор экземпляра агента | `<хост>:0` |

### Запуск

```powershell
# терминал 1 - брокер сообщений
docker compose up -d

# терминал 2..5 - агенты с логами и метриками
$env:METRICS_INTERVAL = "2s"
foreach ($a in @("classifier","knowledge","responder","escalation")) {
    $env:LOG_FILE = "logs\$a.log"
    $env:INSTANCE_ID = "$a-1"
    go run "./agents/$a"
}

# терминал 6 - демонстрация логирования и мониторинга
$env:LOG_FILE = "logs/orchestrator.log"
python -m orchestrator.demo_metrics
```

В сводке агентов `responder` отсутствует — это и есть признак того, что агент

### Как устроен сбор метрик

Снимок идентифицируется парой «агент + экземпляр». По умолчанию все агенты
на одном хосте получают `instance` вида `<хост>:0`, и если бы ключом был
только `instance`, метрики агентов затирали бы друг друга: на первой
проверке в сводке был виден только `escalation` с чужими счётчиками. Эта же
схема различает экземпляры одного агента в задании 7.

Счётчики в снимке не уменьшаются: если агент перезапустился с нуля, первый
снимок после перезапуска не обнуляет накопленную статистику.

Метрики публикуются по таймеру, а не в ответ на задание, поэтому таблица
метрик в демонстрации печатается после ожидания очередного тика публикации.

Каталог `logs/` не коммитится, образцы записей приведены выше.

## Задание 6. Обработка ошибок и таймаутов

### Что сделано

Оркестратор повторяет задание при сбое агента: `orchestrator/retry.py`
содержит `RetryPolicy` и функцию `send_with_retry`, через которую проходят
все четыре шага конвейера. При повторе отправляется то же задание с тем же
`task_id`, поэтому агент узнаёт повтор по идентификатору. Пауза между
попытками растёт геометрически и слегка разбросана, чтобы повторы нескольких
обращений не совпали по времени.

Таймаут ожидания результата задаётся переменной `TASK_TIMEOUT` и реализован
в `NatsConnection.send_task` через `asyncio.wait_for`. При исчерпании
попыток наружу поднимается последняя ошибка — причина провала не теряется.

Чтобы повторы было на чём показать, агент умеет изображать сбой: переменные
`FAULT_FAIL_ATTEMPTS`, `FAULT_DELAY_MS` и `FAULT_DROP` включают в него
искусственные ошибки, задержки и молчание. По умолчанию они выключены, а при
включении агент пишет об этом в лог.

### Настройки

| Переменная | Назначение | По умолчанию |
|------------|------------|--------------|
| `TASK_TIMEOUT` | сколько ждать ответ агента на одну попытку, с | 5 |
| `MAX_ATTEMPTS` | попыток отправки всего, включая первую | 3 |
| `RETRY_DELAY` | пауза перед первым повтором, с | 0.5 |
| `RETRY_BACKOFF` | во сколько раз растёт пауза | 2.0 |
| `RETRY_MAX_DELAY` | верхняя граница паузы, с | 5.0 |
| `RETRY_JITTER` | доля случайного разброса паузы | 0.1 |
| `RETRY_ON_AGENT_ERROR` | повторять ли при ошибке агента | true |

### Про «не более 3 раз»

Методичка требует повторять задание не более трёх раз. По умолчанию задано
`MAX_ATTEMPTS=3` — три попытки всего: одна первая и две повторные. Три
повтора дали бы четыре отправки, и требование было бы превышено. Значение
вынесено в настройку.

ошибкой на первые две попытки, потом он не отвечает вовсе.

## Задание 8. Создание API для запуска задач

### Что сделано

REST API на FastAPI принимает обращение клиента, проводит его через
оркестратор и агентов и возвращает ответ: HTTP → API → оркестратор → агенты →
ответ.

Логика вынесена из HTTP-слоя в `api/state.py`: класс `AppState` отвечает за
подключение к NATS, метрики агентов и хранение результатов и не зависит от
FastAPI, поэтому её можно проверять в тестах без запуска сервера. Само
приложение собирается функцией `create_app(state)`, которой в тестах
передаётся состояние с подменёнными зависимостями.

| Метод | Путь | Назначение |
|-------|------|------------|
| `GET` | `/health` | состояние API, NATS и список агентов |
| `GET` | `/api/agents` | метрики агентов и счётчики оркестратора |
| `POST` | `/api/tickets` | обработать обращение и вернуть ответ клиенту |
| `POST` | `/api/tickets/async` | принять обращение в работу, вернуть его номер |
| `GET` | `/api/tickets` | последние обработанные обращения |
| `GET` | `/api/tickets/{ticket_id}` | результат одного обращения |

Коды ответа выбраны по смыслу сбоя: 200 — обработано, 202 — принято в
асинхронную обработку, 422 — запрос не прошёл проверку, 502 — агент ответил
ошибкой, 503 — нет соединения с NATS, 504 — агент не ответил за отведённое
время.

Тело запроса проверяется схемой: от 5 до 2000 символов, лишние поля
запрещены. Middleware пишет метод, путь, код и время обработки; время также
возвращается в заголовке `X-Process-Time-Ms`.

### Запуск

```powershell
docker compose up -d
python -m api.main
```

API доступен на `http://127.0.0.1:8000`, документация OpenAPI — на
`http://127.0.0.1:8000/docs` (она формируется по схемам Pydantic).

Пример запроса:

```bash
curl -X POST http://127.0.0.1:8000/api/tickets \
  -H "Content-Type: application/json" \
  -d "{\"text\": \"Не могу оплатить заказ, карта не проходит\"}"
```

### Проверка

```powershell

```

Демонстрация сама собирает и поднимает агентов, запускает настоящий сервер
отдельным процессом и обращается к нему по HTTP.
