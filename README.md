## Задание 2. Разработка прототипа агента на Go

Первый агент - классификатор тикетов. Он подписывается на очередь NATS,
принимает структурированный JSON, выполняет логику классификации и
публикует результат в общую тему ответов.

### Запуск

```bash
# терминал 1 - брокер сообщений
docker compose up -d

# терминал 2 - агент
go build -o classifier ./agents/classifier
./classifier
```

### Проверка

Задания публикуются в тему `ticket.classify`, ответы приходят в
`ticket.result`. Подписка видна в мониторинге NATS:

```bash
curl "http://127.0.0.1:8222/subsz?subs=1"
```

```json
{"subject": "ticket.classify", "queue_name": "classifiers"}
```

**Обработка ошибок:** задание с пустым текстом обращения не роняет агента,
а возвращает результат с ошибкой - оркестратору нужно знать, что задание
не выполнено.

### Как устроен агент

Общая обвязка вынесена в отдельный пакет, агент пишет только свою логику:

| Файл | Назначение |
|------|------------|
| `pkg/messages/messages.go` | типы сообщений `Task`, `Result`, темы NATS, константы категорий |
| `pkg/agent/agent.go` | подключение, подписка на очередь, разбор JSON, вызов обработчика, публикация результата, счётчики, graceful shutdown |
| `pkg/agent/writer.go` | запись лога одновременно в файл и в консоль |
| `agents/classifier/main.go` | правила классификации и функция `handleTask` |
| `agents/classifier/errors.go` | ошибка для пустого текста обращения |

Контракт: агент реализует `handleTask(messages.Task) (messages.Result, error)`.
Всё остальное делает базовый пакет.

### Порядок правил важен

Правила проверяются по порядку, и первое совпадение задаёт категорию.
Порядок выбран так, чтобы неоднозначные обращения попадали в более
серьёзную категорию: фраза «Не работает оплата картой» содержит и
«не работает», и «оплата», но проверяется первым правилом `technical` и
получает приоритет 5, а не 4. При алфавитном порядке правил приоритет был
бы занижен.

## Задание 3. Разработка оркестратора на Python

### Как устроен оркестратор

| Файл | Назначение |
|------|------------|
| `orchestrator/config.py` | настройки из переменных окружения: `NATS_URL`, `TASK_TIMEOUT`, `MAX_ATTEMPTS`, `RETRY_DELAY` |
| `orchestrator/messages.py` | модели Pydantic, повторяющие контракт из `pkg/messages/messages.go` |
| `orchestrator/client.py` | подключение к NATS, подписка на результаты, отправка заданий, ожидание ответа, таймауты |
| `orchestrator/main.py` | демонстрация: пять обращений и проверка таймаута |

### Раздача ответов по идентификатору задания

Агенты публикуют результаты в общую тему `ticket.result`, а не отвечают
адресно. Оркестратор подписывается на неё один раз и раздаёт ответы
ожидающим заданиям:

```python
self._pending[task.task_id] = future   # при отправке
future = self._pending.pop(task_id)    # при получении ответа
```

Ответ, для которого нет ожидающего задания, попадает в лог с
предупреждением и никого не будит — так система переживает зависшие задания
и повторные ответы.

### Обработка таймаутов

```python
try:
    result = await asyncio.wait_for(future, timeout=timeout)
except asyncio.TimeoutError as exc:
    self._pending.pop(task.task_id, None)
    raise TaskTimeoutError(...) from exc
```

При таймауте будущее удаляется из словаря ожидающих, чтобы поздний ответ
агента не остался висеть.

Таймаут проверен отправкой задания в тему `ticket.no_such_agent`, на
которую никто не подписан: оркестратор ждал ровно секунду и поднял
`TaskTimeoutError`.
