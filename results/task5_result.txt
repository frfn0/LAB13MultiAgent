Задание 5. Логирование и мониторинг: фактический вывод
======================================================

Дата проверки: 2026-10-07
Инструменты: NATS 2.10.29 (nats:2.10-alpine), Go 1.26.1, Python 3.10.6, ruff

Что сделано
-----------

1. Структурное логирование в агентах (Go).

   Пакет pkg/agent использует slog: каждая запись пишется в JSON-совместимом
   виде "время уровень сообщение ключ=значение". Ключевые значения (task_id,
   ticket, elapsed_ms, agent, subject, queue, interval) передаются полями
   атрибутов, поэтому их можно фильтровать, не разбирая текст сообщения.

   Все записи идут одновременно в stderr и в файл, если задан LOG_FILE.
   Без LOG_FILE агент пишет только в stderr - это поведение по умолчанию.

   Переменные окружения агента:
     LOG_FILE          путь к файлу лога (необязательно)
     LOG_LEVEL         DEBUG включает подробные записи
     METRICS_INTERVAL  период публикации метрик, например "5s"
     INSTANCE_ID       идентификатор экземпляра (необязательно)

   Запуск с логом в файл:

     $env:LOG_FILE = "logs\classifier.log"
     $env:LOG_LEVEL = "INFO"
     go run ./agents/classifier

   Фрагмент logs/classifier.log:

     time=2026-10-07T19:44:08.385+03:00 level=INFO msg="агент запущен" agent=classifier subject=ticket.classify queue=classifiers nats=nats://127.0.0.1:4222
     time=2026-10-07T19:44:08.433+03:00 level=INFO msg="публикация метрик запущена" agent=classifier interval=2s
     time=2026-10-07T19:44:33.510+03:00 level=INFO msg="задание выполнено" task_id=task-ebc6dcf3 ticket=ticket-24fa0c46 elapsed_ms=0

2. Публикация метрик агентами.

   Добавлена тема agent.metrics и тип Metrics в контракт сообщений
   (pkg/messages/messages.go). Каждый агент раз в METRICS_INTERVAL публикует
   снимок своих счётчиков:

     type Metrics struct {
         Agent          string `json:"agent"`
         Queue          string `json:"queue"`
         Instance       string `json:"instance"`
         Received       int64  `json:"received"`
         Processed      int64  `json:"processed"`
         Failed         int64  `json:"failed"`
         UptimeSeconds  int64  `json:"uptime_seconds"`
     }

   Публикация не зависит от наличия заданий: метрики идут и в простое,
   поэтому по ним видно, что агент жив, даже когда трафика нет.

3. Сбор метрик в оркестраторе.

   Новый модуль orchestrator/metrics.py с классом MetricsCollector:
     - подписка на agent.metrics;
     - снимок последних значений по каждому экземпляру;
     - счётчики самого оркестратора: tasks_sent, tasks_failed, timeouts;
     - сводка по агентам (agents), по именам (by_agent) и общая (totals);
     - summary_line - одна строка для лога оркестратора.

   Снимок идентифицируется парой "агент + экземпляр". Это важно: по умолчанию
   все агенты на одном хосте получают instance вида "<host>:0", и если бы ключом
   был только instance, метрики агентов затирали бы друг друга. На это наступил
   первый прогон: в сводке был виден только escalation с чужими счётчиками.
   Пара "агент + экземпляр" заодно решает задачу 7, где экземпляров одного
   агента будет несколько и складывать их счётчики по имени нельзя.

   Значения счётчиков никогда не уменьшаются: если агент перезапустился с
   нуля, первый снимок после перезапуска не обнуляет накопленную статистику.

4. Логирование в оркестраторе.

   Логи идут в консоль и в файл, задаётся переменной LOG_FILE. Формат:
   "время уровень имя модуля сообщение". Библиотека nats-python переведена
   на WARNING, чтобы её внутренние сообщения не забивали вывод.

   Счётчики коллектора увеличиваются в конвейере на каждом шаге:
     classify    -> count_sent()
     find_article-> count_sent()
     make_answer -> count_sent()
     escalate    -> count_sent()
   Обработчик run_pipeline_safe увеличивает count_timeout() и count_failed()
   при таймауте и при любой ошибке шага.

Запуск демонстрации
--------------------

Поднимаем NATS и агентов с логами и метриками:

  docker compose up -d
  $env:METRICS_INTERVAL = "2s"
  foreach ($a in @("classifier","knowledge","responder","escalation")) {
    $env:LOG_FILE = "logs\$a.log"
    $env:INSTANCE_ID = "$a-1"
    Start-Process -FilePath ".\$a.exe" -WindowStyle Hidden
  }

  $env:LOG_FILE = "logs/orchestrator.log"
  python -m orchestrator.demo_metrics

Полный вывод: results/task5_output.txt

Найденные при проверке дефекты
------------------------------

1. Колбэк подписки на тему в nats-py обязан быть корутиной. Обычный
   def on_metrics приводил к ошибке "nats: must use coroutine for
   subscriptions". Исправлено: метод стал async.

2. Тема agent.metrics была добавлена только в Go-контракт
   (pkg/messages/messages.go), но отсутствовала в Python-зеркале
   (orchestrator/messages.py). Оркестратор падал с ImportError.

3. Снимки метрик ключевались только по instance. При одинаковом instance
   у всех агентов на одном хосте сводка показывала данные одного агента
   вместо данных четырёх. Исправлено: ключ "агент:экземпляр".

4. В шаг escalate не передавался коллектор, поэтому tasks_sent не учитывал
   эскалации: 15 вместо 16 при одном обращении, ушедшем человеку.

5. Таблица метрик печаталась сразу после обработки и показывала нули:
   агенты публикуют снимки по таймеру, а не в ответ на задание.
   Добавлено ожидание очередного тика публикации перед выводом.
