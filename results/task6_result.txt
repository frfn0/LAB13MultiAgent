Задание 6. Обработка ошибок и таймаутов: фактический вывод
=========================================================

Дата проверки: 2026-10-07
Инструменты: NATS 2.10.29 (nats:2.10-alpine), Go 1.26.1, Python 3.10.6, ruff

Требование методички
--------------------

"Реализовать в оркестраторе механизм повторной отправки задачи при сбое
агента (retry, не более 3 раз). Добавить таймаут ожидания результата."

Что сделано
-----------

1. Повторная отправка в оркестраторе — orchestrator/retry.py.

   RetryPolicy задаёт параметры повторов:

     max_attempts        попыток всего, включая первую (по умолчанию 3)
     initial_delay       пауза перед первым повтором, с
     backoff             во столько раз растёт пауза
     max_delay           верхняя граница паузы, с
     jitter              доля случайного разброса паузы
     retry_on_agent_error  повторять ли при ошибке в ответе агента

   Функция send_with_retry отправляет задание и при сбое повторяет его,
   сохраняя тот же task_id, поэтому агент узнаёт повтор по идентификатору.
   При исчерпании попыток наружу поднимается последняя ошибка — причина
   провала не теряется.

   Все четыре шага конвейера (классификация, поиск статьи, ответ,
   эскалация) идут через send_with_retry.

2. Таймаут ожидания результата.

   Задаётся переменной окружения TASK_TIMEOUT (по умолчанию 5 с) и
   передаётся в каждый шаг отдельно. Реализация — asyncio.wait_for в
   NatsConnection.send_task, ошибка — TaskTimeoutError.

3. Управление сбоями в агенте — pkg/agent/agent.go.

   Чтобы повторы было на чём показать, агент умеет изображать сбой.
   По умолчанию сбои выключены, включаются переменными окружения:

     FAULT_FAIL_ATTEMPTS=N  ответить ошибкой на первые N заданий
     FAULT_DELAY_MS=N       задержать ответ на N миллисекунд
     FAULT_DROP=1           принять задание и не ответить вовсе

   При старте агент пишет в лог предупреждение о включённых сбоях, поэтому
   в логах видно, что сбой искусственный.

4. Учёт в мониторинге.

   tasks_sent теперь считает попытки отправки, а не задания: одно задание
   с двумя повторами занимает три попытки. Добавлен счётчик retries.
   Каждый таймаут считается по факту, включая те, после которых был
   повтор, - иначе неудачные попытки, закончившиеся успехом, были бы
   не видны.

Настройки
---------

| Переменная | Назначение | По умолчанию |
|------------|------------|--------------|
| `TASK_TIMEOUT` | сколько ждать ответ агента на одну попытку, с | 5 |
| `MAX_ATTEMPTS` | попыток отправки всего, включая первую | 3 |
| `RETRY_DELAY` | пауза перед первым повтором, с | 0.5 |
| `RETRY_BACKOFF` | во сколько раз растёт пауза | 2.0 |
| `RETRY_MAX_DELAY` | верхняя граница паузы, с | 5.0 |
| `RETRY_JITTER` | доля случайного разброса паузы | 0.1 |
| `RETRY_ON_AGENT_ERROR` | повторять ли при ошибке агента | true |

Про «не более 3 раз»
---------------------

Методичка требует повторять не более трёх раз. По умолчанию задано
MAX_ATTEMPTS=3, то есть три попытки всего: одна первая и две повторные.
Такое прочтение выбрано потому, что «три повтора» дали бы четыре отправки
задания, и требование было бы превышено. Значение вынесено в настройку,
поэтому при необходимости его легко изменить.

Запуск
------

  docker compose up -d
  python -m orchestrator.demo_retry

Демонстрация сама собирает агентов, поднимает их и останавливает, а сбои
включает по фазам. Полный вывод: results/task6_output.txt

Найденные при проверке дефекты
------------------------------

1. Повторы не срабатывали: кроме нужного экземпляра агента работал ещё
   один, здоровый, экземпляр того же агента. Оба стояли в одной группе
   очереди "responders", и задания доставались здоровому, а сбоящий
   экземпляр их не видел. В демонстрации постоянные агенты теперь не
   включают ответчик - он запускается заново на каждой фазе.

2. Параметр policy в run_pipeline и run_pipeline_safe оказался перед
   metrics, из-за чего коллектор и политика менялись местами: демонстрация
   падала с AttributeError: 'RetryPolicy' object has no attribute
   'count_failed'.

3. Промежуточные таймауты, после которых был повтор, не попадали в
   счётчики: их учитывал только run_pipeline_safe и только последний.
   Учёт перенесён в send_with_retry, чтобы видеть и неудачные попытки.
