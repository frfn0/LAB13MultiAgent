Задание 8. Создание API для запуска задач: фактический вывод
===========================================================

Дата проверки: 2026-10-07
Инструменты: NATS 2.10.29 (nats:2.10-alpine), FastAPI 0.135.3,
uvicorn 0.43.0, httpx 0.28.1, Go 1.26.1, Python 3.10.6, ruff

Требование методички
--------------------

"Разработать простой REST API на FastAPI (Python), который принимает запросы
на выполнение задач (HTTP → оркестратор → агенты → ответ)."

Что сделано
-----------

1. Приложение API (api/app.py).

   Маршруты:

   | Метод | Путь | Назначение |
   |-------|------|------------|
   | GET | `/health` | состояние API, NATS и список агентов |
   | GET | `/api/agents` | метрики агентов и счётчики оркестратора |
   | POST | `/api/tickets` | обработать обращение и вернуть ответ клиенту |
   | POST | `/api/tickets/async` | принять обращение в работу, вернуть его номер |
   | GET | `/api/tickets` | последние обработанные обращения |
   | GET | `/api/tickets/{ticket_id}` | результат одного обращения |

   Документация OpenAPI доступна на `/docs` и формируется по схемам Pydantic,
   отдельно её писать не пришлось.

2. Логика вынесена из HTTP-слоя (api/state.py).

   Класс AppState отвечает за подключение к NATS, метрики агентов и хранение
   результатов. Логика не зависит от FastAPI, поэтому её можно проверять
   в тестах без запуска сервера. Само приложение собирается функцией
   create_app(state), которой в тестах передаётся состояние с подменёнными
   зависимостями.

3. Коды ответа выбраны по смыслу сбоя.

   | Код | Когда |
   |-----|-------|
   | 200 | обращение обработано |
   | 202 | обращение принято в асинхронную обработку |
   | 422 | запрос не прошёл проверку (короткий текст, лишние поля) |
   | 502 | агент ответил ошибкой |
   | 503 | приложение не подключено к NATS |
   | 504 | агент не ответил за отведённое время |

4. Проверка входа (api/schemas.py).

   TicketCreate требует от 5 до 2000 символов и запрещает лишние поля
   (extra="forbid"): опечатка в имени поля больше не проходит молча.

5. Логирование запросов.

   Middleware пишет метод, путь, код ответа и время обработки; это же время
   возвращается в заголовке X-Process-Time-Ms.

6. Асинхронное принятие.

   POST /api/tickets/async возвращает 202 и номер обращения, а конвейер
   работает в фоне. Ответ забирается запросом GET /api/tickets/{ticket_id}.
   Результаты последних 200 обращений хранятся в памяти - этого достаточно,
   чтобы забрать ответ, и не тянуть в проект полноценное хранилище.

Запуск
------

  docker compose up -d
  python -m api.main

  API на http://127.0.0.1:8000, документация на http://127.0.0.1:8000/docs

Проверка выполняется демонстрацией, которая сама собирает и поднимает
агентов, запускает настоящий сервер отдельным процессом и ходит к нему по
HTTP:

  python -m api.demo_api

Полный вывод: results/task8_output.txt

Найденные при проверке дефекты
------------------------------

1. В теле ответа часть полей отсутствовала там, где обращение не
   эскалировалось: assigned_to приходил как null вместо пустой строки,
   хотя в документации это поле объявлено со значением по умолчанию.
   Причина - маршруты отдавали словарь напрямую, минуя схему. Теперь ответ
   прогоняется через TicketResponse, и тело всегда соответствует схеме.

2. На /health список агентов был пустым, а в метриках агентов стояли нули.
   Метрики публикуются по таймеру, а первая проверка шла сразу после старта
   сервера: первый снимок агентов прошёл до подписки API. Добавлено
   ожидание снимка перед проверками.

3. Пустые значения в таблице вывода печатались пробелами и выглядели как
   пропущенные данные. Теперь пустая строка печатается как прочерк.

4. Случайно осталась попытка измерять длительность запроса через
   logging.getLogger().time() - такого метода у логгера нет, время
   считается через time.perf_counter().

5. В демонстрации стоял ошибочный ключ процесса агента: ключ строится как
   "имя-экземпляр", из-за чего остановка агента-ответчика в шестом пункте
   не срабатывала и проверка отказа агента проходила бы с работающим
   агентом.
