Задание 10. Документирование архитектуры: фактический вывод
=========================================================

Дата проверки: 2026-10-07
Инструменты: NATS 2.10.29, Go 1.26.1, Python 3.10.6, pytest 9.0.3, ruff

Требование методички
--------------------

"Создать диаграмму взаимодействия агентов (PlantUML или Mermaid) и описание
каждого компонента системы."

Что сделано
-----------

1. Документ docs/architecture.md.

   Выбран Mermaid: диаграммы рисуются прямо на GitHub без установки
   PlantUML, и остаются текстом, который можно править в том же репозитории.

   Разделы документа:

   | Раздел | Содержание |
   |--------|------------|
   | 1. Обзор | назначение системы и роль оркестратора |
   | 2. Диаграмма компонентов | состав системы и связи между частями |
   | 3. Диаграмма последовательности | успешное обращение по шагам |
   | 4. Диаграмма конвейера | ветвление: решение найдено или эскалация |
   | 5. Диаграмма повторов | что происходит при сбое агента |
   | 6. Описание компонентов | каждый компонент: файл, назначение, поведение |
   | 7. Темы NATS и сообщения | направления тем и примеры JSON |
   | 8. Настройки | переменные окружения и значения по умолчанию |
   | 9. Отказоустойчивость | что сделано и чего сознательно нет |
   | 10. Запуск всей системы | команды для запуска и проверки |

2. Диаграммы в Mermaid.

   - Компоненты: клиент, REST API, оркестратор, брокер NATS, четыре агента,
     общая обвязка агента, контракт на двух языках, база знаний.
   - Последовательность успешного обращения: HTTP-запрос, три шага конвейера
     с ответами по идентификатору задания, ответ клиенту.
   - Конвейер с ветвлением: найдена статья или эскалация человеку, с
     повторами при сбое агента.
   - Повторы при сбое: таймаут, пауза, три попытки с тем же
     идентификатором задания, успех с третьей попытки.

3. Описание каждого компонента.

   Для каждого указаны файл, назначение и поведение, а для агентов - очередь
   и правила работы: порядок правил классификатора, сопоставление слов по
   общему началу в поиске, детерминированность генератора ответа, формат
   номера эскалации.

4. Соответствие документации коду проверяется тестами.

   Новый файл tests/test_documentation.py, 66 тестов: все шесть тем NATS
   упомянуты, все компоненты описаны, все упомянутые файлы существуют,
   значения по умолчанию в таблицах совпадают с кодом, диаграммы написаны на
   поддерживаемом языке Mermaid и содержат сообщения в корректном синтаксисе.

   Проверка значений по умолчанию идёт через настройки приложения, а не через
   зашитые в тест числа: иначе расхождение в тесте и в коде осталось бы
   незамеченным.

5. Схема в README.

   В README добавлен короткий раздел «Архитектура» с той же схемой в
   компактном виде и ссылкой на подробный документ: при открытии репозитория
   состав системы виден сразу.

Найденные расхождения между документацией и кодом
------------------------------------------------

1. В README для METRICS_INTERVAL было указано значение по умолчанию `5s`,
   а в коде агента задано `10 * time.Second`. Тест на значения по умолчанию
   это сразу показал. README исправлен.

2. В docker-compose был включён JetStream флагом `-js`, хотя система
   работает на обычных темах NATS: задания отправляются через publish, а
   ответы приходят в общую тему `ticket.result`. Включённый JetStream создаёт
   ложное впечатление, что задания переживают перезапуск брокера и
   хранятся в потоке. Флаг убран, в файле оставлен комментарий, а в
   разделе «Отказоустойчивость» перечислено, что постоянного хранилища нет.

   После перезапуска брокера с новой конфигурацией перепрогнаны все
   демонстрации: demo_pipeline, demo_metrics, demo_retry, demo_instances и
   demo_api вернули код 0.
